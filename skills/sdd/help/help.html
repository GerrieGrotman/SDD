sdd help

Spec-driven work on Azure DevOps items: one folder per work item, scripts do the mechanics, you make the decisions. First time? Follow steps 1 to 5. Already set up? Jump to Every command.

From a fresh workspace to your first fixed bug and your first spec item. Do the steps in order. Every step that changes something asks you first. Run every command from the workspace: the folder above your repos.

1

Set up once

/sdd init

sdd shows a table of checks: Python, Node, git, the Azure CLI login, .claude/sdd.json, the CLAUDE.md block. For each one that is missing it shows the fix and asks Yes or Skip. Required ones come first.

  • az login is yours to run. Type ! az login at the prompt, then let sdd check again.
  • When sdd.json is missing, sdd asks which folder holds the specs (default docs/spec). Drop any ADO project that holds no specs.
Done when every required check is ok and .claude/sdd.json exists. Restart Claude Code once, so the ELI5 output style loads.
2

Pull the specs

/sdd sync <epic id>

Sync copies work items from ADO into your spec folder. It is a script: it costs no tokens.

  1. Pick the epic or feature your team works under and type its id.
  2. sdd says how many folders it will write, and asks. Say yes.
  3. You get one folder per item: <spec folder>/…/<id>-<TYPE>-<slug>/requirements.md.
Never edit requirements.md. It mirrors ADO, and the next sync overwrites it. A spec is wrong? Fix the work item in ADO, then sync again.

Later: /sdd sync refreshes everything already synced. /sdd sync all pulls every item in every project; use it rarely.

3

Check the blast radius

/sdd impact <story id>

Impact finds what else an item touches, so you catch gaps before you write code. A script finds the candidates; Claude judges only those.

  1. Open impact.md, next to the item's requirements.md.
  2. It lists the items that are affected, and the questions that raises: gaps, contradictions, missing links.
  3. Decide what to do with each question. Ask the author in ADO, or note it and go on.

/sdd impact all does this for the whole spec. It costs tokens, so it shows an estimate and asks first.

4

Your first bug

/sdd <bug id>

Use a small Bug or Issue. sdd reads the type and starts the bug flow. All edits happen in .claude/worktrees/<id>-<slug>/src/<Repo>/, never in your main checkout.

sdd workssdd stops for you
  1. Load and claimMirrors the bug, assigns it to you.You: pick the team version.
  2. Branch and worktreeMakes the work item folder, a git worktree per repo, and a code graph.
  3. Validate, reproduce, root causeChecks the bug against its story, reproduces it, traces the real cause.
  4. ApprovalA written problem, cause and fix summary. No code changes before this.You: approve, or send it back.
  5. Red test, fix, verify, pushA failing test first, then the fix, proved red to green.
  6. Manual verificationAsks you to check the fix yourself.You: say it works, or choose to skip.
  7. PR and write-backRaises the PR. Writes root cause and resolution back to ADO.
  8. PR reviewWaits for the review.You: say approved, merged or rejected: why.
After the PR merges, run /sdd done <id> to clean up.
5

Your first spec item

/sdd <story id> full

Use a story or tech story. sdd starts the spec flow. It first asks for the path: full keeps every stop; short approves design and tasks together in one stop. Say it up front (short or full) or sdd asks. For a first run, pick full.

sdd workssdd stops for you
  1. SpecifyClaims the item, mirrors it, runs impact.You: pick the path.
  2. Open QuestionsAsks the questions in questions.md, one by one.You: answer, or say "Continue with this open".
  3. RequirementsShows the requirements as understood.You: approve.
  4. DesignWrites design.md after reading the real code. Skipped on the short path.You: approve.
  5. DecomposeWrites tasks.md. May propose tech stories.You: approve.
  6. ImplementOne task at a time, each with its tests.
  7. VerifyChecks drift from the spec and overlap with other work.You: approve.
  8. ReviewRaises the PR and waits.You: say approved, merged or rejected: why.

requirements.md is the ADO mirror. design.md and tasks.md are yours: sync never touches them.

Bugs and issues (Claude Desktop app)

/sdd-bugsThe bug manager. Sync from ADO pulls the bugs and issues into the spec folder; ⚙ Config opens .claude/sdd.json, where the categories are. Pick a category (quick wins, high severity, in progress, ready for deployment, team branch version), filter (by words, type, state, Assigned to me, Hide resolved/closed, or Dev team, the developers in .claude/developers.json; its areaPath limits what is shown at all), and open a row to triage it.
/sdd-bugs mineThe same, with only the items assigned to you.
Triage a rowState, severity, priority, assignee, area, iteration, tags and a comment. Each change is staged first. Save all to ADO writes the batch; ↶ reverts one change, Revert item one item, Revert all the batch. Tick rows to change several at once.
Probable causeEvidence only searches your repos with git (no tokens). Find probable cause sends the report and that evidence to a small model once, and keeps the answer.
Start or continue sdd📋 Copy /sdd <id> puts the command on the clipboard: paste it in a new chat to start the flow, or to continue it where it stopped. In this chat puts /sdd <id> in the prompt box.

Check on it, finish or stop

/sdd status <id>Where it stands: ADO state, the step reached, tasks done, PRs.
/sdd <id> feedback <stage>: <text>Back to a done or waiting stage with your feedback.
/sdd done <id>After the PRs merge and the work item is closed out. Shows what goes, then asks.
/sdd abandon <id>Stop an item and clean up what it created. Asks before anything outward-facing.

Both done and abandon refuse, and say why, when the item is not in the right state.

Where things live

Work item folder: .claude/worktrees/<id>-<slug>/

  • src/<Repo>/: your code. Every edit, build, test and commit happens here.
  • graph/: code graph of src/. Start with GRAPH_REPORT.md.
  • workitem.json: which repo is on which branch, its PR, and where the flow stopped.

Spec folder: specRoot in .claude/sdd.json, then **/<id>-<TYPE>-<slug>/

TYPE is EPIC, FEAT, US, TS, CR, PBI, BUG or ISSUE.

  • requirements.md: mirror of ADO. Never edit it; the sync overwrites it.
  • questions.md: open questions for the item's author, one - [ ] line each. While any is open, the flow stops at Open Questions and asks them one by one. You can answer "Continue with this open" to go on anyway.
  • design.md, tasks.md, impact.md: yours. The sync never touches them.
  • .index/spec.db (at the spec folder root): search index.
  • .bugs/ (at the spec folder root): the bug manager's copy of the bugs and issues (index.json, items/) and your unsaved changes (pending.json).

Rules

  • The flow stops for your approval before code changes, before a PR, and before cleanup.
  • Every question comes as a pick-list, with links to the spec documents and code it is about.
  • Say abandon at any point to stop and clean up.
  • Specs change in ADO, not in the files: fix the work item, then /sdd sync.
  • Never edit in the main checkout. Only in src/<Repo>/.

Update sdd

Get the newest version from a chat. Type each line with a ! in front, so it runs as a shell command:

  1. !claude plugin marketplace update sdd: pulls the newest marketplace list.
  2. !claude plugin update sdd@sdd: updates the plugin.
  3. Run /reload-plugins, or start a new chat, so the new version loads.
